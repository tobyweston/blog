Why TDD is Dead

Say fareware to the golden age of test driven developemnt

Published: Jul 18, 2026

For many years, I’ve thought of myself as a TDD evangalist. I’ve put in my 10,000 hours of deliberate practice with TDD and have found it to be an extremely powerful too when building software. I’ve been using and teaching the technique since the early days of eXteme Programming and have worked with many world class developers doing so. I know its a tool much more about design than it is about testing. I love it.

So why am talking about the death of TDD?

AI

It started with skills. As I started using AI when coding my development practice began to change. I started with basic interactions and auto complete and as the tools evolved and my confidence in them rose, I started to leverage more and more techniques to kind of pre-train the coding assistance to produce code that I liked.

For example, I built up the usual catalouge of SKILLS.mds, mostly containing guidance from the golden era of TDD.

---
name: xp-programmer
description: 'Apply testing and extreme-programming (XP) TDD practices from the golden age of test-driven development; use whenever writing, reviewing, or refactoring unit tests or the code under test.'
---

When writing unit tests, favor stubs over mocks.

Try and tease out behavioural contracts and break up complex classes to make them easier to test with simple stubs.

This often means passing in collaborators as interfaces or traits and using constructor injection to supply test doubles.

Favour modern testing techniques and libraries that encourage good test design, such as property-based testing, test data builders, and fluent assertions.

Use matchers for rich error reporting and practice a red, green, refactor workflow.

Clearly express the behavioural contract of the code under test in the test names and structure, so that the tests serve as documentation for how the code is supposed to work.
